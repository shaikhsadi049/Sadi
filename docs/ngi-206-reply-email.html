Thanks, I have looked at NGI-206 (NGI XFINT – difference in the maximum length of bdiMemo1 between NGI and IL). Summary of where this stands and what I need to close it:

Category Details
Issue NGI XFINT enforces a maximum length of 35 characters on bdiMemo1, so a transaction with a longer memo fails STP. The same transaction through IL reaches STP with a bdiMemo1 longer than 35 characters.
Analysis The limit is almost certainly a Bean Validation constraint (@Size(max = 35)) on the bdiMemo1 field of the XFINT request payload. These NGI services validate the request body at the controller, so the transaction is rejected before any database call is made – which is consistent with the transaction failing STP outright rather than part way through posting. Being confirmed against the XFINT sources and the DB function it calls.
Point to confirm first Important: 35 characters is also a common narrative/memo width in FCR, so the limit may reflect a real downstream column width rather than an arbitrary NGI validation. That IL reaches STP tells us IL does not reject the transaction; it does not yet tell us that the full memo was stored. IL may be passing the whole value to a wider column, truncating silently at 35, or carrying the remainder into bdiMemo2 – and each of those implies a different fix on the NGI side. If we simply widen the NGI validation while the FCR column is 35 wide, we would replace a clear validation error with an ORA-06502 during posting, or with silently truncated data, which is worse than the current behaviour.
Needed from BDI
  1. The XFINT ITRD / field mapping sheet for bdiMemo1 to bdiMemo3, with the agreed maximum length of each field.
  2. One IL transaction reference whose bdiMemo1 was longer than 35 characters, so we can compare what IL stored in FCR against what the channel sent.
  3. Expected behaviour when the memo exceeds the agreed length: reject the transaction, truncate the memo, or carry the remainder into bdiMemo2.
  4. From the Jira: the failing request payload, the exact error NGI returned, and the svcRqId / trace id so the request can be located in the UAT log.
Items 1 and 2 are the ones that decide the fix; item 4 only confirms which layer holds the limit.
