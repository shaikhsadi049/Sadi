I have resolved the issue for NGI XFINT (Jira NGI-206 – difference in the maximum length of bdiMemo1 between NGI and IL). Please find the resolution details and deployment prerequisites below:

Category Details
Issue A transaction with bdiMemo1 longer than 35 characters did not reach FCC, so it could not be straight through processed, while the same transaction through IL did. The channel received responseCode 0000000, so the failure was not visible from the NGI side.
Analysis Root cause in the DB package PK_OL_XFINT, function AP_OL_XFINT_S_MAIN, where the FCUBS message is built.
  • The entire memo was placed in a single <PAYDET1> element, with PAYDET2 to PAYDET5 sent empty. PAYDET is one line of MT103 field 70, which is 4*35x, so one element carries 35 characters and FCC did not accept 60.
  • On a rejected FCC reply the package sets its internal swift flag to 0, which skips the PM_TXN_LOG update to TXN_STAT = 1 / MSG_STAT = 5 and the channel_swift_payment_xref insert, but still returns 0000000 to the channel. That is why the legs posted and the channel saw success while the message was never sent.
Confirmed against the UAT defect log of 14 October: the same request with a 35 character memo reached FCC (ext_ref_no 7101262870000118) and the 60 character one did not (7101262870000116), every other field being identical.
Fix Details Two changes, both inside the XML block of AP_OL_XFINT_S_MAIN:
  • Memo split across PAYDET1 to PAYDET4, 35 characters each, which is the 140 character capacity of MT103 field 70. For the reported case PAYDET1 now carries the first 35 characters – exactly the value FCC already accepted on the 35 character run – and PAYDET2 carries the remaining 25.
  • SWIFT_X added, a body level function that reduces free text to the SWIFT X character set. Free text was previously concatenated into the request unescaped, so a memo containing & or < would make the request malformed and be rejected for a reason unrelated to length. This matches IL, whose own FCC message carries WILLIAM AGUS`SE as "WILLIAM AGUS SE" while keeping the slash in 001/012.
Nothing outside the FCC message is changed. ORIGINAL_REMIT_NO still takes SUBSTR(PI_MEMO1, 1, 35) and everything AP_SAVE_PAYMENT_LOG writes is untouched, so the stored values stay identical to IL's, which cleans the message text only.
Testing Done <to be completed from the UAT run: re-post the 60 character memo and record TXN_STAT / MSG_STAT, the channel_swift_payment_xref row, and the PAYDET1 / PAYDET2 values in fccprd.mstm_com_pmt_in>
Deployment Prerequisite Crucial: the package specification is unchanged, only the body was modified, so no JAR change is required and no DB object is created or dropped.
The script carries a / after the specification and after the body. The source extracted from ALL_SOURCE has neither, and without the one after the specification SQL*Plus does not submit it and reads the body as a continuation of the same statement, which leaves the package INVALID and the service returning PLS-00905.
